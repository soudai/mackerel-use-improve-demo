OBSERVE. UNDERSTAND. IMPROVE.

観測から、
改善のPRへ。

「遅い」を見つけて終わらない。
Laravelの小さな受注アプリで、証拠を集め、コードを直し、同じ条件で効果を確かめる。

デモを起動する ↓シナリオを選ぶ →
ONE IMPROVEMENT LOOP
  1. 01
    観測するメトリックス・ログ・トレース
  2. 02
    原因を確かめる実行計画・対象commitのコード
  3. 03
    IssueからPRへ一つの仮説、一つの変更
  4. 04
    同条件で検証する性能・挙動・品質の前後比較
main = 改善前のベースライン
6改善シナリオ
1共通の基準commit
0事前に埋め込む修正版

各シナリオは demo-before-v2 から始め、
独立したブランチとPRで改善します。

01

一つのアプリで、観測をつなぐ

購入・検索・売上集計の実際の操作を、実行時の挙動とコードの品質に結び付けます。

題材は「ミニEC＋受注・在庫管理」です。注文一覧のN+1、人気商品のロック待ち、検索SQL、大量データの集計、複雑な割引ロジックを含みます。mainには業務上動作する改善前コードを置き、完成済みの修正版へ切り替えるフラグは設けません。

TRAFFIC画面 / 負荷生成同じseed・同じ条件
→
APPLICATIONLaravel + PHP-FPM業務スパン / 構造化ログ
→
DEPENDENCIESPostgreSQL / 配送モック実行計画 / 行ロック
実行時のテレメトリー ↓
COLLECTOTel Collectorトレース / ログ / DB統計
→
DEFAULTローカル成果物artifacts/otel/*.jsonl
⇢
OPT-INMackerel接続を設定して送信
PHPUnit + CCCC→品質bundle・詳細レポート→Mackerelサービスメトリックス

このデモで扱う5つの目的

  1. N+1・ロック待ちなどの性能改善
  2. 認知複雑度・循環的複雑度の継続監視
  3. 全走査・未使用索引・大量行取得の調査
  4. ログから遅いAPIを抽出し、内部処理へ進む
  5. トレースとソースを照合し、Issue・改善PRへ

基準を固定する

demo-before-v2 は初期実装を指す不変のタグです。別の改善を試すたびにこのタグから分岐します。品質の対象は backend/app/。実行していない問題版も静的解析されるため、問題版と修正版を同じコードに共存させません。

02

起動して、改善前を測る

WSLのリポジトリルートで実行します。Docker Engine / Docker Desktop、Compose、Python 3が必要です。

1

cd /home/soudai/work/mackerel/mackerel-use-improve-demo
test -f .env || cp .env.example .env
./scripts/demo setup
curl -fsS http://localhost:18080/up

setup は依存インストール、APP_KEY生成、migration、固定seedの投入、各サービスの起動を行います。画面は http://localhost:18080。フロントエンドのビルド工程はありません。

2

基準タグからブランチを作る

git show --no-patch demo-before-v2

3

負荷と証拠を保存

RUN_ID=$(date -u +%Y%m%dT%H%M%SZ)
python3 scripts/load.py orders --requests 100 --concurrency 4 --warmup 3 \
  --output "artifacts/runs/$RUN_ID/orders-before.json"
python3 scripts/evidence.py \
  --load "artifacts/runs/$RUN_ID/orders-before.json" \
  --output "artifacts/issues/$RUN_ID/orders-before"

各コマンドは新しい出力先を使います。再実行時は RUN_ID を更新してください。Issueの下書きは出力ディレクトリの issue.md に保存されます。通常実行はGitHubへ投稿しません。

停止・テスト・初期データの再作成
./scripts/demo test
./scripts/demo artisan route:list
./scripts/demo logs --tail=100 collector app
./scripts/demo down

down はDBデータを保持します。比較のためにこのデモDBを初期化し直す場合だけ、次を使います。投入する注文数を変える場合は、先に .env を編集してサービスへ反映します。

./scripts/demo reset --yes

この操作はデモDBの既存データを削除し、migrationとseedを再実行します。

03

6つの改善シナリオ

一度に一つ選び、仮説・変更・評価を対応させます。改善案は検証前の候補です。

01注文一覧のN+1↗02在庫引当のロック待ち↗03日付検索の全走査↗04売上集計の大量行取得↗05観測負荷で使われない索引↗06割引ロジックの複雑度↗
01

QUERY COUNT

注文一覧のN+1

codex/demo-n-plus-one

注文が増えるほど、顧客情報を取得するSQLも増える。

最新注文を取得した後、ループ内で顧客リレーションを遅延読込します。注文50件と顧客取得だけなら51回になる構造を、実際のトレースで確認します。

GET /api/orders?limit=50

python3 scripts/load.py orders --requests 100 --concurrency 4 --warmup 3 \
  --output "artifacts/runs/$RUN_ID/orders-before.json"

見る証拠

  • route別のp95、失敗率、X-Query-Count
  • 同じtrace内で反復する顧客取得SQL
  • 取得件数を変えたときのSQL数の増え方

改善の仮説

必要な顧客情報をEager Loadingでまとめて取得する。51→2は取得部分の設計上の例であり、実測値はレポートで確認します。

PRの受入条件

  • 注文の件数・順番・顧客名・金額が同じ。
  • limitを増やしてもSQL数が比例して増えない。
  • p95・DB時間・メモリ・失敗率に回帰がない。
調査を始めるコードbackend/app/Http/Controllers/OrderController.php
02

CONCURRENCY

在庫引当のロック待ち

codex/demo-lock-wait

同じ人気商品への注文が、配送APIの待ち時間まで直列化される。

在庫行をロックした状態で配送見積りAPIを待ちます。PHP-FPMと配送モックは並行処理できるため、同じ在庫行の競合を観測できます。

POST /api/checkout

python3 scripts/load.py checkout --requests 40 --concurrency 12 --warmup 1 \
  --timeout 60 --output "artifacts/runs/$RUN_ID/checkout-before.json"
# 負荷中に別のターミナルで実行
python3 scripts/db_snapshot.py --output "artifacts/db/$RUN_ID/checkout-during.json"

見る証拠

  • 在庫取得スパンと配送HTTPスパンの時間
  • pg_stat_activityのLock待機・blocking PID
  • 成功注文数、在庫減少数、タイムアウト

改善の仮説

配送見積りを先に取得し、在庫を再確認・更新するトランザクションを短くする。ロック件数だけでは、待ち時間や競合の原因を判断しません。

PRの受入条件

  • 在庫が負数にならず、成功注文数と在庫減少数が一致。
  • 配送失敗で不完全な注文や在庫減少を残さない。
  • ロック待ちとp95が改善し、失敗率が悪化しない。
調査を始めるコードbackend/app/Services/CheckoutService.php
03

QUERY PLAN

日付検索の全走査

codex/demo-order-search

狭い期間の検索でも、多くの行やブロックを読む。

状態・日時に合う複合インデックスがなく、日時列には日付変換を適用しています。実行計画と選択率を確認し、どちらが効いているかを調べます。

GET /api/orders/search?status=paid&from=2026-01-01&to=2026-01-02

python3 scripts/load.py search --requests 100 --concurrency 4 \
  --output "artifacts/runs/$RUN_ID/search-before.json"
python3 scripts/db_snapshot.py --explain-search \
  --output "artifacts/db/$RUN_ID/search-before.json"

見る証拠

  • クエリ別の時間・読込ブロック・返却行数
  • EXPLAIN ANALYZEのSeq Scan・Sortなど
  • 検索条件の選択率とseed件数

改善の仮説

UTCの日付境界を保持して半開区間に書き換え、状態・日時・並び順に合う複合索引を検討する。改善後のSQLに合わせた実行計画も取得します。

PRの受入条件

  • 日付の両端、状態、降順、同時刻のid順、limitを保持。
  • 同じ検索結果について読込量・p95を比較。
  • 小規模テーブルの合理的なSeq Scanを障害と断定しない。
調査を始めるコードbackend/app/Http/Controllers/OrderController.php

DATA TRANSFER

売上集計の大量行取得

codex/demo-sales-report

少量の集計結果を返すために、大量の明細をPHPへ転送する。

対象の注文・明細を全件取得してから、PHPで注文数・販売数量・日別金額を集計します。DB転送とPHP処理の両方を分けて観測します。

GET /api/reports/sales?from=2026-01-01&to=2026-02-01

見る証拠

  • reports.fetch_rows / reports.aggregate の時間
  • SELECT返却行数と実行回数の差分
  • アプリのメモリとリクエスト時間

改善の仮説

SQL側で集約し、APIに必要な集計行だけを取得する。DBからアプリへの返却行数と、最終HTTPレスポンスの大きさを区別します。

PRの受入条件

  • 対象状態・日付境界・注文数・数量・売上が一致。
  • ゼロ件、数量2以上、複数明細の注文も正しく集計。
  • 返却行数・メモリ・p95を同じデータで比較。

INDEX USAGE

観測負荷で使われない索引

codex/demo-unused-index

廃止した検索機能のインデックスが残っている。

現在のAPIはlegacy_referenceで検索しません。全業務の負荷を流す前後で、利用統計・サイズ・制約用途を保存して候補を見つけます。

orders_legacy_reference_idx

python3 scripts/db_snapshot.py --output "artifacts/db/$RUN_ID/index-before.json"
# 商品・注文・検索・購入・集計・見積りの代表負荷を実行
python3 scripts/db_snapshot.py --output "artifacts/db/$RUN_ID/index-after.json"

見る証拠

  • pg_stat_user_indexesのidx_scanとサイズ
  • primary / unique / 制約への依存
  • 観測期間、DB・クエリ統計のリセット情報

改善の仮説

業務上の用途と依存関係がないと確認したうえで、削除と復元ができるmigrationを作る。短時間の利用0回は、永久に不要という証明にはなりません。

PRの受入条件

  • 月次・移行・外部利用・制約用途を確認。
  • 全業務と制約の動作を維持。
  • 必要に応じて同じ書込み負荷で容量・更新コストを比較。
調査を始めるコードbackend/database/migrations/2026_01_01_000000_create_demo_tables.php

CODE QUALITY

割引ロジックの複雑度

codex/demo-pricing-complexity

会員・数量・クーポン・送料の追加条件が深い入れ子になる。

認知複雑度と循環的複雑度を別々に測定します。最初に解析の完全性・全関数の明細・価格計算の仕様テストを確認してから、構造を整理します。

PricingService::calculate

./scripts/install-tools
python3 scripts/quality.py

見る証拠

  • cccc.php_static.cognitive.* / cyclomatic.*
  • analysis.complete、対象ファイル数・関数数
  • PHPUnit結果・全関数明細・ソースmanifest

改善の仮説

業務規則を決定表で確認し、条件や責務を整理する。別の巨大関数への移動や、解析対象の除外で指標だけを下げる変更を避けます。

PRの受入条件

  • 価格・割引・送料・クーポン条件の振る舞いを保持。
  • 関数分割後も明細と差分を確認。
  • 複雑度低下だけで高速化や未知のバグ減少を主張しない。

04

証拠を、レビューできる変更にする

アクセスログは入口を絞り、トレースは時間の内訳を示し、コードとDB情報で仮説を確かめます。

  1. 遅いrouteを見つける

    アクセスログの期間・revisionを絞って、p95、失敗、代表trace IDを取り出します。

  2. 同じtraceの処理を読む

    HTTP・SQL・業務子スパンから時間を使う場所を確認します。ネストしたスパンの時間は単純合算しません。

  3. 対象commitのソースへ進む

    service.versionとコード属性を照合します。未コミット状態・別revision・欠測は、確定したソース帰属にしません。

  4. 根拠付きIssueを作る

    期間、再現条件、確認済みの事実、原因仮説、ソース位置、受入条件を残します。

  5. 一つの変更をPRにする

    回帰テストと同条件のbefore/afterを添え、性能・挙動・品質の結果を分けて説明します。

python3 scripts/log_summary.py --output "artifacts/logs/$RUN_ID/routes.json"
python3 scripts/evidence.py \
  --load "artifacts/runs/$RUN_ID/orders-before.json" \
  --output "artifacts/issues/$RUN_ID/orders-before"

log_summary.py は --since / --until / --revision で絞れます。evidence.py はローカルOTLP JSONと負荷レポートのtrace IDを照合し、成果物からIssue下書きを作ります。全メソッドの実行時間や行番号が、自動計装だけで得られるわけではありません。

Issue・PRに含めるもの

観測期間・環境・revisionseed・負荷・ウォームアップ条件trace・ログ・DBの証拠対象ソースと原因仮説変更内容・受入条件前後値・テスト結果・未確認事項
依頼を受けた段階でGitHub Issueを投稿する

下記はGitHubへの書込み操作です。デモの実施者がIssue作成を依頼した段階で使います。認証済みの gh または対応するGitHubツールが必要です。

python3 scripts/evidence.py \
  --load "artifacts/runs/$RUN_ID/orders-before.json" \
  --output "artifacts/issues/$RUN_ID/orders-publish" \
  --title "注文一覧のN+1を改善する" \
  --create-issue --repo soudai/mackerel-use-improve-demo

MackerelのトレースURLは、画面で確認した実URLを追記します。ローカルのtrace IDだけから、Mackerelへの保存成功を判断しません。

比較時に揃える条件
条件確認すること
データseed件数・内容、購入で増えた注文、消費された在庫。必要なら独立した初期DBを使う。
負荷リクエスト数・同時接続数・対象API・ウォームアップ。ウォームアップは測定母数に含めないが、購入では在庫を消費する。
実行と計装アプリrevision・依存・DB・sampling・収集範囲。修正後も同じ条件を使う。
結果全リクエストと成功リクエストの分布、失敗率、業務結果。失敗が増えて速く見える状態を改善としない。
統計累積値の区間差分、実行回数、リセット時刻。平均やp95を別区間で単純平均しない。
05

ローカルで観測し、Mackerelへ接続する

既定構成はローカルJSONへの保存です。外部への実送信は設定を追加して有効化します。

情報ごとの役割と取得経路
情報デモで使う証拠読み方
HTTP / DB / 業務トレースOTelスパン、service.version、trace IDリクエスト内の反復SQLと時間の内訳を確認。
アクセスログroute、status、時間、query count、trace ID遅いAPIを抽出。内部メソッドの原因はトレースへ進む。
DB基本メトリックスCollectorのPostgreSQL receiver接続・ロック・I/Oなどを確認。ロック件数と待ち時間を混同しない。
DB詳細情報pg_stat_statements、実行計画、index統計、待機情報db_snapshot.pyで別途収集。返却行数と走査行数を区別。
コード品質PHPUnit・CCCCの生レポートと正規化bundle完全性を確認して固定数のサービスメトリックスへ投稿。

DBクエリはLaravelの QueryExecuted で成功した実行を1件のCLIENTスパンとして記録します。demo.db.execution=true が実行の目印です。時間はアプリ側で観測したprepare・execute・fetch（再試行があればその経過を含む）で、DBサーバー内部だけの実行時間ではありません。失敗クエリはこのイベントに出ないため、HTTPエラー・例外とDB側の証拠を併せて確認します。SQLのbindingsは展開せず、PDO自動計装は二重計上を避けるため無効にしています。

A

Mackerelへ実行時データを送る

デモ用の送信先組織を確認し、Write権限のAPIキーを .env の MACKEREL_APIKEY に設定します。キーをcommitしないでください。追加Composeの起動と同時に外部への送信が始まります。

DEMO_MACKEREL=1 ./scripts/demo up
DEMO_MACKEREL=1 ./scripts/demo logs --tail=100 collector

service.name は mackerel-seminar-demo、namespace は demo、環境は development。traces/logsはOTLP HTTP、DBメトリックスはOTLP gRPCを使います。Mackerel側でservice・version・観測期間とデータの到着を確認してください。この資料は実組織への送信・保存・画面表示の検証済みを意味しません。

B

品質レポートを取得する

./scripts/install-tools
python3 scripts/quality.py

CCCC 1.8.3の全件JSON、PHPUnit 12.5.xのXML、独立したテスト一覧、ソースmanifest、品質bundle、投稿dry-run結果を保存します。quality.py は送信しません。まず analysis.complete、解析対象件数、元コマンドの終了結果を確認します。

cccc.php_static.cognitive.max
cccc.php_static.cognitive.over_limit_count
cccc.php_static.cyclomatic.max
cccc.php_static.cyclomatic.over_limit_count
cccc.php_static.analysis.complete

実投稿は、成果物を実際のHTTPS保存先へ置き、cleanな基準commit・run・attemptを照合してから、Skillの publish.py --send --expected-org ... を使います。関数名・ファイル・commitは詳細成果物へ残し、共有系列にPRごとの測定を混ぜません。

設定の検証と収集の限界
docker compose run --rm --no-deps collector validate --config=/etc/otelcol/local.yaml
MACKEREL_APIKEY=validation-only docker compose -f compose.yaml -f compose.mackerel.yaml \
  run --rm --no-deps collector validate \
  --config=/etc/otelcol/local.yaml --config=/etc/otelcol/mackerel.yaml
  • 構文検証の成功は、Mackerelへの接続・認証・保存の成功とは別です。
  • Collectorのメモリ内queue・有限retryには欠落の可能性があります。停止や欠測を「問題が解消した」と扱いません。
  • ログの読取位置は artifacts/otel/checkpoints に保存します。checkpoint削除やログの再配置で再読込が起こり得るため、期間・trace IDで絞ります。
  • APM受信スパン数は、負荷生成の全リクエスト数と一致するとは限りません。

06

変更後も保持する業務仕様

性能改善と業務上の正しさを同時に確かめるため、金額・在庫・日付境界を固定します。

データと在庫

顧客・商品・在庫・注文・注文明細を持ちます。seedは固定乱数 20260101、注文日時はUTCの2026年1月。商品ID 1の初期在庫は100,000です。既存の商品があるとseedをスキップし、追加投入しません。

購入は既存顧客・有効商品・数量1〜100を受け付けます。在庫確認、減算、注文と明細作成を原子的に行い、配送失敗ではロールバックします。単品購入APIの合計は単価×数量＋配送APIの送料です。

一覧・検索・集計

  • 注文一覧：id降順、limit既定50、範囲1〜100。
  • 検索：状態とUTCの日付範囲、両端含む。created_at降順・id降順、limit既定50、範囲1〜200。
  • 売上：paidだけを対象。注文数は一意な注文ID数、数量は明細数量の合計、金額は数量×単価で送料を含まない。
  • by_dateはUTCの日付順。ゼロ件、境界日、複数明細も検証する。

見積りAPIの価格計算

金額は整数の *_cents。単価1〜1,000,000、数量1〜100で、小計＝単価×数量です。見積りの会員・クーポン規則は、単品購入APIには適用しません。

会員割引率（小計に対して適用・端数切捨て）
会員数量条件割引率
regular20以上 / 20未満5% / 0%
silver10以上 / 5〜9 / 1〜410% / 7% / 5%
gold10以上 / 5〜9 / 1〜415% / 12% / 10%
  1. SAVE10：割引前小計が3,000以上なら、会員割引後の10%を追加割引。端数切捨て、上限2,000。
  2. 送料判定は全割引後の金額を使います。tokyo / osakaは600、10,000以上または FREESHIP で0。速達は最後に400追加。
  3. remoteは1,200、10,000以上なら600。FREESHIP は適用せず、速達は最後に800追加。
  4. 合計＝小計−会員割引−クーポン割引＋送料。
仕様例

単価1,000 × 数量10 / gold / SAVE10 / tokyo / 通常配送
10,000 − 1,500 − 850 ＋ 600 ＝ 8,250 cents

価格の例は仕様上の期待値です。性能の実測結果ではありません。
