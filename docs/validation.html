03

改善できることを、隔離した実験で確かめる

候補コードを本番相当のアプリへ切り替えることなく、同じ入力の結果と構造的な改善を比較しました。

改善前と候補の比較
シナリオ改善前 → 候補維持できたこと
N+1注文50件でSQL 51 → 2回。20件でも21 → 2回、100件では101 → 2回。返却内容が一致。件数に比例するSQL増加を解消できる。
日付検索Seq Scan＋Sort → Index Scan。候補インデックスはトランザクション内で作成し、ロールバック。返却50行が一致。日付の境界と並び順を保持。
売上集計DBからの取得行数 48,000 → 31行。集計結果が一致。必要な日別結果だけを取得できる。
割引計算最大認知複雑度 51 → 8、最大循環的複雑度 29 → 7。4,320通りの有効な入力組合せで結果が一致。

候補比較は単一CLIプロセスの実験です。実行時間は参考値にとどめ、同一結果・SQL数・取得行数・実行計画・複雑度を主な証拠にしています。性能改善の採否を決めるPRでは、同一条件のHTTP負荷による反復比較が必要です。

未使用インデックスは orders_legacy_reference_idx を候補として調査できます。観測した負荷で使われないことと、将来も不要であることは別です。用途・制約・月次処理などを確認する工程を残しています。

04

実接続で見つかった観測の問題を修正

業務上の改善前コードは保持し、デモの証拠を誤って読む原因を取り除きました。

  1. 過去のトレースで取得上限が埋まる問題

    対象trace IDをストリーミング中に絞り込み、該当スパンだけを上限に数えるよう修正。走査量や巨大レコードで打ち切った場合はpartialを返します。

  2. SQLのprepare時間を実行時間と読んでしまう問題

    PDO自動計装のprepareスパンではなく、Laravelの成功した QueryExecuted を1件のCLIENTスパンにしました。アプリ側のprepare・execute・fetchを含む経過時間です。失敗クエリはこのイベントに出ないため、例外・HTTPエラー・DB側の情報で補います。

  3. テストのアクセスログが実リクエストに混ざる問題

    PHPUnit実行中のアクセスログ出力を除外。実サービスと同じ属性で、ゼロtrace IDのテストログを送信しないようにしました。

05

確認できた範囲と、残す工程

「APIから読めた」「画面で見えた」「改善をデプロイした」は、それぞれ別の確認です。

今回確認できたこと

  • 認証済みAPIでのHTTP・DB APM、ログ、品質系列の読戻し。
  • ロック待ちと業務整合性、トレースと同一版ソースの対応。
  • 候補実装による返却内容の一致と、SQL数・行数・複雑度の改善余地。

今回未実施のこと

  • 現在のChromeプロファイルでは対象組織がOrgNotFoundとなり、Mackerel画面の目視確認は未完了。
  • 改善候補のデプロイと、実Issue・改善PRの作成。

取得窓を広げた最終確認では、同時購入のHTTP・DB・ログと品質メトリックスの全信号が complete になりました。analysis.complete=1、認知複雑度max=51、循環的複雑度max=29、テスト選択件数28を読み戻しています。

品質のサービスメトリックスを読むときは、測定時刻の分だけでなく前後に余裕を持たせます。APIの時刻境界が分単位になるため、狭すぎる取得窓は投稿済みの点を取りこぼします。今回の投稿値・metadataの検証自体は verified まで完了しています。
